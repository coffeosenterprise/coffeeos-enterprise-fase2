# ADR-019 — Resolución de Tenant en Login, Refresh y Flujos Públicos

**Estado:** Approved
**Fuente:** Fase 1 v1.1 (correcciones #2, #3, #4 de la revisión de Fase 1)

## Contexto
El modelo permite el mismo email en distintos Tenants (`@@unique([tenantId, email])`, no `@@unique([email])`). Login, Refresh, activación de invitación y reset de contraseña ocurren ANTES de que exista un `TenantContext` — pero las tablas que consultan (`users`, `sessions`, `invitations`, `password_reset_tokens`) tienen RLS y lo exigen.

## Decisión
1. **Cada Tenant tiene un `slug` único** (elegido al crearse). Login y solicitud de recuperación de contraseña lo reciben explícitamente en el request (`tenantSlug`) para resolver el Tenant antes de consultar `users`.
2. **Refresh token, token de invitación y token de reset de contraseña son "tokens compuestos"**: `{tenantId}.{secreto aleatorio}`. El `tenantId` no es secreto (es un identificador, no una credencial) — anteponerlo en claro permite que el endpoint resuelva el Tenant y entre al `TenantContext` correcto sin una tabla de búsqueda global sin RLS. Solo el secreto aleatorio (32-48 bytes) protege la posesión real del token; se almacena únicamente su hash SHA-256.
3. `/auth/refresh` no depende de un Access Token válido — el propio refresh token resuelve tenant y usuario. Es, precisamente, el mecanismo pensado para cuando el Access Token ya expiró.

## Consecuencias
`LoginDto` y `RequestPasswordResetDto` ahora exigen `tenantSlug`. El frontend deberá conocer o solicitar el slug del Tenant antes de loguear (típicamente vía subdominio o un selector de organización — el diseño de esa UX queda fuera de esta fase, es un problema de Fase 2 en adelante).
